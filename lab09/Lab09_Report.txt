1. Inodes and Metadata:
In the inode_inspector.py script, we printed the "Inode Number". If you rename the file using the Linux mv command, will the Inode Number change? Why or why not? (Hint: Think about how the OS separates the file name from the actual data).
- Answer: No, the Inode Number will not change when renaming a file using the mv command. This is because the file name is stored in the directory entry (mapping the name to the Inode), while the actual file metadata (such as size, permissions, and data block pointers) and Inode number remain entirely unchanged on the filesystem.

2. POSIX Permissions:
If you want to set a file's permission so that the Owner has Read/Write/Execute (7), the Group has Read/Execute (5), and Others have absolutely no access (0), what would be the 3-digit octal number you pass into os.chmod() ?
- Answer: 750

3. The AI Context:
Why is it safer to rely on Operating System file permissions (like os.chmod(00444)) to protect production model weights rather than relying solely on application-level logic or Python try-except blocks?
- Answer: Relying on OS-level file permissions is much safer because security enforcement happens at the kernel level. Application-level logic or Python try-except blocks can easily be bypassed by bugs, syntax errors, or malicious code modifications within the application. In contrast, the Operating System acts as an unyielding gatekeeper that intercepts and blocks unauthorized write attempts at the system call level, regardless of what the application code tries to do.
